1The design of record — one owner per job

mihomo decides whether a connection needs a proxy, which upstream proxy it uses, and DNS policy.
HypoMux decides which adapter every dial leaves by — every connection, direct included: proxied dials via dialer-proxy, everything else via the DISPATCH group. It measures the adapters and holds the weights and the strategy.
Chain: apps/system proxy → mihomo → HypoMux → the adapters. Operating mode: system proxy on both components, no TUN anywhere (tun.enable: false; HypoMux mode: proxy with system_proxy_takeover: false).

2The chain, drawn

Drawn as designed, not as inherited: apps/system proxy → mihomo → HypoMux → the adapters, system proxy on both halves, no TUN anywhere — and since the third revision of 2026-10-11 HypoMux is a hop for every connection mihomo handles, direct included (DISPATCH). 3Resolution — mihomo owns the DNS policy (live: disabled, :53 is ICS)

DNS policy is mihomo's job under the design of record: one owner per job, and no second resolver that can bind a literal NIC address and take the machine's DNS down with it. The intended shape is mihomo listening on 0.0.0.0:53 and splitting by destination — domestic names to AliDNS/doh.pub, blocked and data names to 1.1.1.1/8.8.8.8 — with respect-rules: true so its own overseas DoH queries obey the routing rules instead of being dialled direct and poisoned.

Why the DIRECT rules are mandatory — not routing, safety

mihomo dials the HypoMux SOCKS5 endpoint at 127.0.0.1:10800 — that is what dialer-proxy: hypomux means, and the DISPATCH group dials it too — and the SSH tunnel at 127.0.0.1:1080. Point a rule at the proxied path for 127.0.0.0/8 and mihomo is asking a dialer to reach an address on this machine: a NIC-bound socket cannot reach 127.0.0.1, and aiming the dialer's own endpoint at the dialer is a loop. They carry no-resolve for the same reason.

This was a real bug in an earlier revision, and it is why the loop-protection rules are re-checked on any group change: LOCAL existed but zero rules referenced it, so every non-proxied connection silently bypassed the intended path. Under the renewal the same trap applies to HYPOMUX-PATH, and since the third revision it applies to DISPATCH as well — neither may become the target of a rule that can carry loopback or the private ranges. Because the catch-all is MATCH,DISPATCH, the default is not safe by construction any more; these rules are what keeps a destination addressed by IP off the dialer, and they stay. They are also now the only rules that still follow the plain OS route.

Quota isolation — structural, not procedural

AUTO is not url-test, and it never was: under the free-first era it was a fallback that walked HYPOMUX-PATH (the free Aliyun path) first and the clashmi provider after it, so the metered plan was reached only after the free path had failed. The fourth change of 2026-10-11 reversed that ordering on purpose: AUTO is now a load-balance on round-robin whose four 911 exits (chosen by filter:) outnumber aliyun-native four to one, so 4 of every 5 proxied connections spend the metered plan and the free share is what keeps that path exercised. The ratio is by member count, because mihomo groups have no weights; a rename in the subscription silently shrinks it (open item, docs\TODO.md P0e).

LOCAL — the direct lane — is select [DISPATCH, DIRECT] (it was select [DIRECT]) and holds no paid member, so it physically cannot spend the subscription. The previous design's deliberate 1:1 spend (MIX = [HY2LB, PAID]) and the 40 GB byte-counting guard that bounded it were retired together on 2026-10-11: the MIX ring is gone from the config and the guard lived in the watcher that no longer runs. So the mix is not guarded by counting at all — the guard question is an open decision (section 10, docs\TODO.md P0e), and it matters more now than it did under free-first ordering.

5NIC dispatch — HypoMux's job, owned by its GUI

Under the design of record HypoMux decides which adapter each dial leaves by — every connection: proxied dials go through it because mihomo dials 127.0.0.1:10800 (its dialer-proxy), and everything not proxied goes through the DISPATCH group, where the same listener is used as a plain dialer. HypoMux opens the socket from the adapter it picks, measuring each adapter and applying its own strategy and weights. Only loopback and the private ranges stay off it — they remain raw DIRECT on the OS route.

Retired 2026-10-11: the previous design's machinery, and how it went

The generated per-NIC outbounds (aliyun-nic9/aliyun-nic26, hy2-nic9/hy2-nic26, each with interface-name: 以太网 / 以太网 2), the HY2LB and DIRECT-LB rings, the MIX ring, and the AdapterMonitor watcher (src\proxy\Watch-Adapters.ps1) that measured adapters and rewrote those rings were all present in runtime\config.yaml until 12:2x on 2026-10-11, and all of them are gone now: the GENERATED:PROXIES/:AUTO/:LOCAL bodies hold a legacy note only (the six marker lines are byte-identical), and the watcher's task is Disabled with zero Watch-Adapters processes. hypomux-distribution.ps1 (no arguments; -Check gates on 10800, -Restore undoes, -DryRun/-NoReload/-ConfigPath/ -Summary review a scratch copy) is the tested switch that did it — it never starts, stops or reconfigures HypoMux (the GUI owns it), it validates (structural self-check + mihomo -t + no-legacy-names) before stopping the watcher, it reloads via the API, it verifies the proxy 204 and the socket acceptance test, and it rolls config + mihomo + watcher back on any failure. A second run left the config byte-identical (idempotent).

Why NIC selection cannot be automated from this repo (measured 2026-10-11)

The GUI owns the engine: hypomux-engine.exe (pid 23188) is a child of hypomux.exe (pid 16456) and is driven over the GUI's stdio channel — the same line-delimited JSON protocol (engine.hello, engine.start mode=proxy) that hypomux-serve.ps1 speaks.

There is no control API: 10801 is the HTTP proxy port and answers 502 to proxy-style requests, the GUI opens no listening socket of its own, and the only named pipe is \\.\pipe\HypoMux-Core-Service — the idle service engine, with zero connections. The one programmatic route, hypomux-serve.ps1, spawns a separate engine that cannot bind 10800 while the GUI's engine holds it and that the GUI shows nothing about — the operator would be watching a different process than the one carrying traffic.

Consequence: NIC dispatch is human-controlled in the GUI. Repo scripts must not start, stop or reconfigure HypoMux — and hypomux-distribution.ps1 does not: it only gates on 127.0.0.1:10800 and tells the operator to launch the GUI, while hypomux-serve.ps1 is kept as the record of the engine's own protocol.

Trap: HypoMux is now a single point of failure for the whole machine

Before the renewal the catch-all was MATCH,LOCAL — a direct path that could not fail because a component was missing. It became MATCH,HYPOMUX-PATH at 12:2x, and every member of that group is dialled through HypoMux, so for a few hours a closed 10800 took the catch-all down. Later on 2026-10-11 the owner changed the catch-all to MATCH,DIRECT, which removed that failure from the default path — but not from the proxied one: every destination a rule names (our B-class rules, the 911 must-proxy list, the learner's escalations) still goes to AUTO → HYPOMUX-PATH → the HypoMux dialer. The third revision then put HypoMux back in the path of everything, deliberately and with a guard: the catch-all is MATCH,DISPATCH and DISPATCH is a fallback whose second member is DIRECT, so with the engine down the machine keeps the internet — on the OS route, without NIC dispatch — while proxied traffic still fails. Two honest limits come with it: mihomo does not retry a connection that failed on the dispatched path (the fallback is group-level and health-check based, not per-connection), and the GUI has no autostart (section 8), so the engine-down state is reachable in practice rather than theoretical.

Why a proxied dial can be distributed but a plain SSH tunnel cannot

HypoMux distributes independent connections. An SSH -D tunnel multiplexes N streams into one TCP connection — there is nothing to distribute, and the socket belongs to ssh.exe, where neither mihomo nor HypoMux can reach it. Native shadowsocks and anytls both open one connection per stream, and they are dialled by mihomo, so dialer-proxy applies to them and only to them. That distinction is the entire reason for the transport change.

Honest reading of the numbers

  • The headline number is 12.6 ms, and it is history. DNS was 89× faster per query under SmartDNS-rs, but browsers resolve in parallel, so page-load savings are small — and the resolver is not even live now (section 3). Real latency lives in TCP + TLS handshakes.
  • HypoMux gives no raw speedup today — both adapters share one MiFi uplink (identical public IP), so there is nothing to aggregate. Under the renewal its value is not speed: it is one owner for NIC choice, per-dial adapter selection and failover, and being the only layer able to aggregate once a second independent uplink exists. The third revision measured the same parity through the hop itself — baidu 0.204 s through HypoMux vs 0.221 s without it — so making it a hop for everything did not cost latency.
  • Two earlier conclusions of mine were wrong and are retracted: "HypoMux is 9× worse" (measured on a degraded link) and "HypoMux is 2.4× better" (the link recovered mid-test). Only interleaved sampling gave a trustworthy answer.
  • The GUI's stored adapter selection is not what governs. Its settings reported selected_adapter_ids: ["以太网 2"] with adapter_weights: {"以太网 2": 1}, yet the engine used both NICs (21 sockets, 17 + 4). Read the GUI's live numbers as the record; treat the file as stored intent.

Open decisions

Q1 — Retire the SSH tunnel?

Redundant as a transport (no dialer can take over a socket owned by ssh.exe), but under the renewal it is the only proxy path that survives a HypoMux outage — and since the third revision HypoMux carries everything mihomo handles: unlisted traffic included, via DISPATCH, and the group's DIRECT member is what keeps direct traffic online when the engine is down. Every proxied destination — the 911 rule set included — depends on the dialer. That is what makes this dialer-free exit worth keeping. Level 2 of section 7 is the argument.

Keep it — extra resilience, ~2 MB RAM, no cost. Two independent free paths (one of them dialer-free).
Retire it — simpler; removes the AliyunTunnel task and the ssh key plumbing, and accepts that a HypoMux outage leaves only the paid provider.

Q2 — Dashboard: which panels lead? recommended

A live status dashboard exists and is working (index.html; the earlier note — kept as the record — is that /api/status once returned a 141 MB payload, which is what made the panels look broken: state\status.json reached 141 MB and now measures 4.7 KB, with mihomo.connections_active, mihomo.routes[], hypomux.carrying and hypomux.carried_conns live, and all three pages (/, /design, /balance) returning 200 as of 2026-10-11). It shows: component state, group membership, which path each connection took, per-adapter latency and public IP, audit-log hit/miss and failure rate.

Lead with quota + the dialer — "is the paid tier being touched" and "is the dial actually going through HypoMux" are the two questions that would have caught the earlier bugs. The page now answers the second with hypomux.carrying / carried_conns (carrying = true measured 2026-10-11) and with the socket test it points at; it still reads mihomo's API, not HypoMux's engine (section 5), so it can show HYPOMUX-PATH's pick and the carried total, never HypoMux's own per-NIC split.
Lead with component health — mihomo (policy) and HypoMux (dialer) with colour-coded state, plus hotspot, tunnel and learner.

Q3 — Should the dashboard be able to act?

Currently specified as strictly read-only. Buttons could force the free tier, restart the tunnel, or freeze the groups' picks. Anything touching NIC selection or HypoMux's settings is out of bounds for automation (section 5), so an "act" answer has to stop at mihomo's own surface. (The previous design's "apply/freeze the rings" is no longer available to offer — those rings were retired on 2026-10-11.)

Read-only — safe; no way to break the network from a browser tab, and it keeps the "GUI is the operator of record" rule intact.
Add controls — convenient for mihomo's own groups, but a stray click could spend quota or drop the proxy.

Q4 — Second independent uplink?

The only thing that would make aggregation real — and the only thing that would make HypoMux's adaptive-throughput strategy worth more than failover. Earlier the two adapters exited via different cities (223.160.165.198 Jinan vs 111.55.120.64 Shanghai), so the MiFi hardware can expose two paths — it just is not doing so now.

122026-10-12 — the startup control plane (recommended design, for review)

Owner, 2026-10-12: "can you automatically control mihomo and hypomux at windows start/login?" and then "what's your recommendation design now?" — this section is the answer, written as a proposal. Nothing of it is built yet; the last block is the decision list, with recommended values in bold.

Baseline, measured today: the machine is stock — today's resets deleted every task (MihomoSplitter, AliyunTunnel, the hotspot pair, the status window), the logon Run entries are gone, HypoMux's autostart / auto_start_engine are false, and HypoMuxCore is DISABLED / STOPPED. So this design is about re-enabling deliberately, plus one new piece that coordinates the two lanes.

The two lanes — and their one honest asymmetry

lanestartsowner of recordif it fails
mihomo — policy: rules, upstreams, the system proxy at boot — task MihomoSplitter, SYSTEM, +30 s; no logon needed this repo, end to end — the supervisor restarts it, the coordinator verifies it task restarts ×5; the coordinator restarts the task once; then repair / plan-B stand as today
HypoMux — NIC dispatch, :10800 at logon — its engine is GUI-owned; no authenticated client exists before a desktop session gui mode (recommended): the app itself starts its engine. agent mode: this repo runs a headless engine in its place. gui mode: the lane is absent and reported; DISPATCH falls back to DIRECT, so the machine stays online on the OS route

Stated plainly, so nothing promises otherwise

  • No pre-logon HypoMux proxy. The Core Service at boot would be an idle, fingerprint-guarded engine host — the lane begins when the official GUI attaches at logon, and only the official binary may attach. Enabling the service changes the engine's identity, not the timeline.
  • One owner at a time, enforced. An engine's control channel is a private stdio session; two controllers on one engine are impossible by design. The coordinator detects contention (two engines, or :10800/:10801 held twice) and fails loudly, changing nothing.
  • The system proxy is per-user. Even mihomo's :7897 reaches apps only after logon brings the HKCU pointer up — which is exactly the job the new coordinator takes over from muscle memory, and only when mihomo actually answers.
  • One rule pair bypasses the dispatch hop by owner order: the two DeepSeek rules (deepseek.com suffix + deepseek keyword — the keyword is what catches deepseekapi-style hosts) are raw DIRECT: through any proxy DeepSeek is unreachable from here, and through the hop it is what logged the 241 deadline-exceeded dials. fix-deepseek.ps1 re-forces them, and a RepoHygiene test now pins them so a future edit cannot flip them back silently.

What gets added

  • src\startup\StartupCoordinator.ps1 + a logon task (+20 s, interactive user, hidden and conhost --headless like every other interactive task): bounded waits for :7897/:9097 and (gui mode) :10800; sets the HKCU system proxy to mihomo only when mihomo answers; single-owner checks; runs start-network.ps1 --check as the single source of truth; writes state\startup-<stamp>.log and feeds the status window. Scoped repairs only — it never resets network, never edits configs, never drives the GUI engine.
  • config\startup-policy.json (tracked): mihomo: task|off · hypomux: gui|agent|off · systemProxy: auto|off · aliyunTunnel: task|off · hotspot: logon|off · hypomuxService: auto|off. Recommended defaults: task · gui · auto · task · logon · off. autostart-on/off.bat, reset-network.ps1 and fixall.ps1 keep covering every registered name — the way-out guarantee stays whole.
  • agent mode only — runtime\hypomux-agent-supervisor.ps1: a resident supervisor (the mihomo-supervisor.ps1 pattern) that starts and holds a headless engine over protocol v1 — live engine.scheduling, telemetry snapshots into state\ — for unattended and benchmark runs. The GUI's own auto-start-engine must be off in this mode, and the coordinator enforces that the two never overlap.

Why gui mode is the recommendation

The rule has been no script drives HypoMux, and it stays right: the engine's control plane is one private session, and the GUI's value is a human watching the numbers. gui mode keeps that — HypoMux starts itself at logon (its own Run entry and settings), the coordinator only verifies and reports, and the operator keeps the NIC dials. agent mode is the honest tool for the opposite case — runs where nobody is watching the GUI — and the protocol makes it real: engine.start, live engine.scheduling (adapters, weights, strategy mid-run), engine.telemetry, engine.stop. What it cannot offer is visibility: the GUI would show nothing about an agent engine, so that mode reports telemetry itself.

Decisions requested recommended values in bold

  1. HypoMux lane at logon: gui · agent · off — and if gui, may the coordinator relaunch hypomux.exe --silent when the process is missing (yes — starting the app, not driving it), or strictly report?
  2. Re-enable the mihomo boot task now? yes — the machine is stock since today's resets.
  3. System proxy: set it automatically at logon, only when mihomo answers? yes — this retires the most common "no internet" state the plan-B doc records.
  4. AliyunTunnel back at boot? yes — the dialer-free independence path (§7). Hotspot tasks: logon as before (the phone flow uses them), or off / on demand?
  5. HypoMuxCore service: off — flip it later only for a TUN-ready posture; it never yields a pre-logon proxy.
  6. Keep the visible NetworkStatus window at logon as the human readout, with the coordinator's summary appended to the same log? yes.

The day this is approved and built, it supersedes §8's "launched by hand" row for the HypoMux lane and the "cannot be driven" limit in §10 — with the ownership rule intact, gui or agent, never both.
